When does split computing pay off for UAV object detection?

A measured and simulated study with YOLOv8 and 18 other detectors: what was built, how it was measured, which assumptions were made, what the results show, and what they mean.

Student Utkarsh Sengar Code uav-split-perception (branch publication-overhaul) Paper paper/main.pdf, 12 pages Date 29 Sep 2026

SummaryThe answer in one page

A drone films at 30 frames per second and must detect objects in every frame. It can run the detector onboard (slow computer, no network needed), send each frame as a JPEG to a ground server (fast GPU, needs bandwidth), or use split computing: run the first few layers onboard and send the intermediate feature maps. Split computing is often proposed as the best of both. This project tests that claim carefully.

What was done. I built a toolkit that splits YOLOv8s exactly at any layer, compresses what crosses the cut, and sends it in a secure packet format. I measured accuracy on all 5,000 COCO validation images, measured sizes and timings on a GPU, and simulated the whole drone system (camera, onboard computer, radio link, deadline, battery) over synthetic 5G channel traces. I then generalized: a closed-form model that covers every parameter, 19 detectors, five input sizes, aerial images (VisDrone), bit widths from 2 to 8, and 1,300 randomly drawn systems.

Main finding

Splitting is exact, and compressing the split tensors to 8 bits costs no measurable accuracy. But the smallest split payload is still 2.4× a high-quality JPEG (Q95) for YOLOv8s, and 2.0–11.5× a JPEG Q90 across 19 detectors. So sending the JPEG wins almost everywhere. Across 1,300 random systems, whenever the image needs fewer bytes and less onboard work, a split can beat it by at most its tiny accuracy advantage (0.47 % observed). Split computing helps over running onboard when the drone's computer is slow and the link is decent, and an adaptive policy that can choose onboard, split or JPEG is the most robust option.

Section 1The research question

UAVs used for inspection, search and rescue or surveillance need object detection at video rate. The computer a drone can carry is limited by weight and power, so detection is slow onboard. A ground server with a GPU is fast, but the wireless uplink is limited and fluctuates. There are three ways to run a detector such as YOLOv8:

flowchart LR
  C[Camera frame] --> A{Choice per frame}
  A -->|1 Onboard| O[Whole network on the drone] --> R[Detections]
  A -->|2 Split at layer k| E[Layers 0..k on drone] --> Q[Quantize + compress] --> L((Uplink))
  A -->|3 Image offload| J[JPEG encode] --> L
  L --> S[Ground server]
  S --> CL[Remaining layers k+1..22] --> R
  S --> FD[JPEG decode + whole network] --> R

The question: under which conditions (link quality, drone computer speed, deadline, number of drones, detector, image content) does option 2 beat options 1 and 3? The measure of success is the number of correct detections delivered within a 300 ms deadline per second, weighted by detection accuracy.

Why it matters. Many papers propose split computing for drones and edge devices, but often compare against uncompressed images, evaluate on small image sets, or model the network loosely. A careful, reproducible comparison tells practitioners when splitting is worth the engineering effort.

Section 2Background concepts

2.1 Object detection and YOLOv8

An object detector outputs boxes with a class and a confidence for each object in an image. YOLO detectors do this in one forward pass of a convolutional neural network. YOLOv8s (the "small" model) has 11.17 million weights and needs 28.8 GFLOPs per 640×640 image. Its 23 layers form a backbone (layers 0–9, extracts features), a neck (10–21, combines scales) and a head (22, predicts boxes). The neck re-uses earlier layers' outputs through skip connections: for example, layer 15 reads layer 4. After the network, non-maximum suppression (NMS) removes duplicate boxes.

2.2 Measuring accuracy: IoU and mAP

IoU (intersection over union) measures how well a predicted box overlaps a true box. A prediction counts as correct if its IoU is above a threshold. Average precision (AP) is the area under the precision–recall curve of one class. mAP@[.5:.95], the standard COCO metric used throughout, averages AP over 80 classes and ten IoU thresholds from 0.50 to 0.95, and is reported in points (×100). YOLOv8s scores 44.4 on COCO val2017 in our measurement (61.1 at IoU 0.5).

2.3 Split computing and the "live set"

Cutting after layer k means the drone runs layers 0…k and the server runs k+1…22. Because of skip connections, the server may need several tensors, not just layer k's output. The set of tensors that must cross the cut is the live set:

2.4 Quantization

Feature maps are 32-bit floats. Quantization stores them with fewer bits. The main scheme is per-tensor symmetric INT8:

S = max|X| / 127 (one scale per tensor, stored as float32) q = clamp(round(X / S), −128, 127) (1 byte per value, sent) X̂ = q · S (reconstructed on the server) error bound: |X − X̂| ≤ S/2 for every value (Proposition 1 in the paper)

Other modes tested: per-channel INT8, asymmetric UINT8, UINT8 with 99.9 % outlier clipping, FP16, and (for generalization) 2- to 7-bit versions of the same scheme. SQNR (signal-to-quantization-noise ratio, dB) measures reconstruction quality.

2.5 Compression

zstd is a fast lossless compressor; it shrinks INT8 feature maps 2.3–2.6× without changing any value. JPEG and WebP are lossy image codecs tuned to human vision, controlled by a quality Q (1–100). H.264 is a video codec, used here intra-only (each frame independent) via libx264. The key trade-off is bytes sent against accuracy kept.

2.6 Wireless link

Link quality is described by SINR (signal-to-interference-plus-noise ratio, dB). It varies slowly through shadowing (buildings, terrain; log-normal, spatially correlated by the Gudmundson model) and quickly through fading (multipath; Rician with a line-of-sight path, speed set by Doppler). The achievable rate comes from the 3GPP TR 36.942 mapping, a standard "attenuated Shannon" formula. Goodput is the useful delivered rate after losses. Drones sharing a cell split its capacity by water-filling; drones can also relay through each other over Wi-Fi (802.11ax).

2.7 Drone energy

Hovering dominates a quadcopter's power. Momentum theory gives hover power = thrust × induced velocity ÷ (figure of merit × motor efficiency) ≈ 109.9 W for a 1.2 kg drone, compared with about 10 W for compute and 3.8 W for the radio. So the perception strategy barely changes flight time for a normal-sized drone.

2.8 Statistics

Paired bootstrap: to test whether configuration B is really worse than A, resample the images with replacement many times, recompute mAP(B) − mAP(A) on the same resampled images, and take the middle 95 % as a confidence interval (CI). If the CI contains zero, the difference is not statistically significant. Student-t intervals summarise simulation results over 5 random seeds. Spearman rank correlation (ρ) measures how strongly a parameter moves an outcome, from −1 to +1.

4.1 Accuracy measurement

  1. Run the standard Ultralytics validation (confidence 0.001, IoU 0.7, 101-point interpolation) on all 5,000 COCO val2017 images at batch size 1, so each frame gets its own quantization scale, as on a drone.
  2. For a split configuration, attach hooks to the unsplit model that quantize and dequantize exactly the live tensors at the point where the server reads them. Edge layers keep full-precision inputs, exactly as in a real split; a test confirms that this equals running the real edge, quantizer and cloud.
  3. For a codec, encode and decode the network's input image with JPEG, WebP or H.264 before detection.
  4. Compare each configuration with the uncompressed baseline using a paired bootstrap over images (300 resamples for split accuracy, 200 for codecs and the generalization study), giving a 95 % confidence interval for the change in mAP.

4.2 Size and timing

Payload sizes come from serializing real feature maps of 200 letterboxed validation frames with the actual packet format. Each stage (edge layers, quantize, serialize, deserialize, dequantize, cloud layers, NMS) is timed separately on the GPU with synchronisation, after warm-up. NMS for timing uses deployment thresholds (confidence 0.25, IoU 0.45).

4.3 System model

For each option c (onboard, split at k, or image codec) the model uses a few numbers: φc, the fraction of the network's FLOPs run onboard; ρc, other onboard work (quantizing, or JPEG encoding) relative to the full model's time; bc, bits sent; sc, server time; Ac, accuracy. With onboard full-model time T, goodput B, one-way delay d, deadline D and camera rate F:

onboard time e_c = T · (φ_c + ρ_c) latency L_c = e_c + b_c / B + d + s_c bandwidth for deadline B*_c = b_c / (D − e_c − d − s_c) frame rate f_c = F / ceil(F · max(e_c, b_c / B)) utility (the metric) U_c = f_c · [B ≥ B*_c] · A_c / A_ref = accuracy-weighted on-time detections per second

Scaling all onboard work (network layers and JPEG encoding alike) by the same hardware factor T / thost keeps the comparison fair: no strategy gets a speed advantage the others don't.

4.4 Channel traces

Traces are synthetic and labelled as such: 10 ms slots, SINR = mean + Gudmundson-correlated log-normal shadowing + Rician fading at 3.5 GHz (simulated at 1 kHz, averaged per slot), rate from 3GPP TR 36.942 (α = 0.4, at most 2 bit/s/Hz, zero below −10 dB). Four profiles:

4.5 Simulator

  • Time advances in 10 ms slots; the camera produces a frame every 33.3 ms.
  • The onboard processor handles one frame at a time; frames arriving while it is busy are skipped.
  • The uplink keeps only the newest waiting frame (old frames are useless in real time); goodput = trace bandwidth × (1 − residual loss).
  • Transfers that can no longer meet the 300 ms deadline are aborted. A frame is on time if its result is ready at the server within 300 ms of capture.
  • Swarms: drones share a 100 Mbit/s cell by water-filling. Optional relaying: a drone whose goodput estimate drops below 5 Mbit/s sends the frame over 802.11ax to the neighbour with the best estimate (at least 15 Mbit/s). The drone-to-drone link includes path loss, per-pair shadowing (σ = 3 dB) and packet errors with rate adaptation: 59.7 Mbit/s at the 50 m spacing, zero beyond about 840 m.
  • Every setting is run with 5 seeds; results are means with 95 % t-intervals.

4.6 Adaptive policy

For each frame the policy chooses the option with the highest expected on-time, accuracy-weighted throughput:

score_c = f_c · p_c · A_c / A_FP32 − 0.05 · E_c p_c = P(goodput ≥ B*_c), with goodput ~ Normal(μ, σ²) from running (EWMA, 200 ms) estimates; σ is floored at 0.1·μ so the policy is never over-confident E_c = energy per frame (a small tie-breaker) switch only if the new option scores ≥ 5 % higher (hysteresis, prevents flapping)

Two variants: adaptive (onboard/split) chooses among onboard and splits only; adaptive (all) can also choose JPEG or WebP at several qualities.

4.7 Generalization studies

  • Theory: closed-form propositions derived from the model above, valid for any parameter values.
  • Detectors: 19 models from 5 families (YOLOv5u, v8, v9, v10, 11; nano to extra-large). For each: exactness at every cut, per-cut payload on 50 frames, the smallest-payload cut, n-bit sizes. For 10 of them, full COCO accuracy at 8, 6 and 4 bits and JPEG Q90.
  • Input size: 320, 480, 640, 960, 1280 px.
  • Aerial imagery: VisDrone2019-DET val (548 images). VisDrone classes are mapped to COCO classes (pedestrian and people → person, car and van → car, bicycle, motor, truck, bus → their counterparts; tricycles and ignored regions dropped), and COCO-trained detectors are applied without retraining.
  • Bit width: 2 to 8 bits at the k4 cut of YOLOv8s on all 5,000 COCO images.
  • Monte Carlo: 1,000 single-drone and 300 swarm scenarios. Each draws all 22 system variables at random (swarms add the number of drones and cell capacity: 24), then simulates all 43 measured configurations and both policies on the same channel realisation, and records what the closed-form model predicts.

Section 6Results: accuracy and size

6.1 Splitting is exact

Without compression, splitting YOLOv8s at every one of its 22 cuts gives bit-identical output to the unsplit model (tolerance zero, checked by the tests). Any accuracy change below therefore comes from compression alone.

7.5 Swarms sharing a cell, and relaying

  • The fixed k4+zstd split collapses from 6.5 to 0.0 on-time frames/s per drone at 20 drones: it needs the most bandwidth, so it chokes first.
  • Adaptive (all options) degrades gracefully: 29.7 → 16.6 (moderate), 28.5 → 16.7 (blackout).
  • Adaptive (onboard/split) ends at 4.1–4.3, slightly below onboard's 5.0, because its estimate of its share of the cell lags actual contention.
  • Relaying rarely helps: only 36 of 2,254 relayed split frames arrive on time, against 463 of 540 relayed JPEG frames. Relaying never raised throughput by more than 0.0 frames/s and lowered it by up to 0.3, because the shared cell, not the individual link, is the bottleneck.

7.6 Energy

Perception power (compute + modem) is 7.8–12.9 W against about 110 W for hovering. Flight endurance on a 55.5 Wh battery ranges only from 24.2 to 25.1 minutes across all strategies. For normal-sized multirotors, the choice is about latency and throughput, not battery life.

8.1 Theory that holds for any parameter values

The paper states five propositions. Each is proved in the paper and checked by the proof script and by property tests on random inputs.

2Offload dominance. 8.3 Input size and aerial imagery

  • Input size: for YOLOv8s the ratio to JPEG grows from 3.4× at 320 px to 5.3× at 1280 px; JPEG exploits the extra redundancy of larger images. Across all 43 model/size/imagery combinations the smallest ratio is 2.0×.
  • Aerial images (VisDrone): JPEG Q90 frames are 78.4 KiB at 640 px (87.5 for COCO) and 222.2 KiB at 1280 px (214.5). The split-to-JPEG ratio is 3.2× at 640 px and 4.0× at 1280 px, slightly lower than on COCO (3.5× and 5.3×) but far above one.
  • Aerial accuracy (zero-shot, so absolute mAP is low: 10.7 at 640 px, 17.8 at 1280 px for YOLOv8s): at 1280 px the INT8 split (901.1 KiB) changes mAP by −0.02 [−0.06, +0.01] and JPEG Q95 (299.4 KiB) by −0.04 [−0.13, +0.05]; neither is significant. Small aerial objects do not make high-quality JPEG disproportionately harmful.

Section 9Is the simulator right? Validation against ns-3, OMNeT++ and a real network stack

The system results of Sections 7–8 come from our own Python simulator. A simulator written by the authors can only be trusted if an independent tool gets the same answers. We therefore rebuilt every network element of the study in two independent packet-level simulators, ns-3.48 and OMNeT++ 6.3 (with the INET 4.5.4 and Simu5G 1.6.0 libraries), and ran the real Linux network stack with the real frames, codecs and models. Every check is scripted in validation/, and its raw output is stored in experiments/results/validation/.

Verdict

Every model element that network simulators can check agrees with them, or errs on the conservative side, meaning against splitting and against relaying where it matters. All conclusions of the paper hold when the simulator's links are replaced by ns-3's, when cells are shared as unfairly as a real 5G scheduler shares them, and when relays forward packet by packet. One check could not be done: Simu5G does not carry large frame bursts reliably, so frame streaming is checked in ns-3 and over the real stack instead.

Section 10Final inference

  1. Splitting a YOLO detector can be made exact. Computing the live set gives bit-identical results at every cut, for all 19 detectors tested.
  2. Accuracy is not the obstacle. 8-bit quantization of the crossing tensors costs at most 0.04–0.05 mAP points, statistically undetectable in almost every case.
  3. Size is the obstacle. The best split payload is 2.4× a Q95 JPEG for YOLOv8s and 2.0–11.5× a Q90 JPEG across detectors. Larger models, larger inputs and fewer bits all make it worse or cost too much accuracy.
  4. Therefore image offload wins almost everywhere. Fixed JPEG beats every fixed split in all 16 main settings and in 96.6 % of random systems; where a split wins, it wins by less than half a percent, exactly as Proposition 2 predicts.
  5. Split computing is still better than running onboard when the drone's computer is slow and the link is decent (10 of 16 settings). The rule of thumb is β = bandwidth × onboard time ÷ payload > 1.
  6. Adaptivity is the practical recommendation. A policy that can choose onboard, split or JPEG per frame, using uncertainty-aware bandwidth estimates, is within a few percent of the best choice in almost every scenario and handles blackouts by falling back to onboard.
  7. Relaying and energy are secondary. Relaying through neighbouring drones does not help in a shared cell, and the strategy changes flight time by under a minute except on very small drones.
Answer to the research question

For unmodified YOLO detectors, split computing pays off only against onboard inference on a slow drone with a decent link. Against a properly compressed image it essentially never pays off, because the network's own intermediate features are a much less compact code than a JPEG of nearly the same detection accuracy. Making splitting competitive requires a learned, task-specific compression layer at the cut, and this toolkit can evaluate such a layer without changes.

Section 11How the results are verified

  • 118 automated tests: packet parsing and every rejection case, HMAC; quantizer error bounds for every mode and bit width; 22-cut exactness and checkpoints; hooks equal a real split; simulator conservation, capacity and frame-rate rules; drone-to-drone link model; channel statistics against theory; packet-level relay forwarding; CUDA kernel bit-identical to Python; random-input property tests of the propositions.
  • Proof checker (scripts/verify_math_proofs.py): 40 checks, 19 proved symbolically with SymPy and 21 verified against the code and result files.
  • Generated numbers: all 529 numbers in the paper are LaTeX macros written by scripts from the result files; docs/claims_to_evidence.md lists each macro, its value and its source. A validator checks every citation, figure, table and macro before the PDF is built.
  • Statistics: 95 % paired-bootstrap intervals on the full validation sets; 5 seeds with t-intervals for simulations; all random seeds fixed and documented.
  • Bibliography: all 38 references checked against Crossref (DOIs added, metadata corrected).
  • Independent simulators: every network element re-built in ns-3.48 and OMNeT++ 6.3 (INET, Simu5G), plus a real-stack emulation (Section 9); make validate and make validate-omnetpp re-run them.
  • Reproducibility: pinned package versions; make reproduce regenerates every result, table, figure and the PDF (about 7 hours on a laptop GPU). Long runs are cached and resumable.

Section 12Limitations

  1. No drone hardware. Onboard speed and power are parameters, not measurements. The sweep bounds their effect, but a Jetson measurement would be stronger.
  2. Synthetic channel. Traces use standard models whose statistics are validated, and the link and sharing models were checked in ns-3, OMNeT++ and a real-stack emulation (Section 9). These are still simulations, not flight measurements; measured flight traces in the same CSV format can be substituted directly.
  3. Aerial accuracy is zero-shot. Detectors trained on aerial data might respond differently to compression.
  4. No learned bottleneck. The study covers the training-free case; learned feature compression is the natural next step and the only route by which splitting could beat JPEG.
  5. Simplified swarm. One cell, independent policies; drone-to-drone interference and motion are not modelled (both would make relaying worse).
  6. Single-frame H.264. Understates video coding efficiency, which would only favour image offload further.

Section 13Publication value and next steps

Assessment. The work is complete, rigorous and reproducible, and it gives a clear, well-supported negative result with a simple bound that explains it. It is suitable for arXiv now, and realistic for a workshop at a major networking or edge-AI conference, a mid-tier IEEE conference (VTC, WCNC, ICC/Globecom), or a journal such as IEEE Access or Drones. It is not yet a top-venue paper: the core observation (early features are large) is known, the result is negative, and there is no hardware. The simulator is now validated against ns-3, OMNeT++ and a real-stack emulation (Section 9), which removes the most likely methodological objection from reviewers.

What would raise it a tier, in order of impact:

  1. Measure onboard time and power on a real Jetson, ideally with real flight traces.
  2. Train a small learned bottleneck at k4 and show when it beats JPEG in this system model, turning the negative result into a design rule plus a positive example.
  3. Fine-tune detectors on VisDrone so the aerial evaluation is realistic.
  4. Shorten the paper to venue format (abstract ≤ 250 words), and add citations for the YOLOv5/v9/v10/11 detectors used in the generalization.

Time for the drone's computer to run the whole network once.

On-time detections per second, weighted by relative accuracy.

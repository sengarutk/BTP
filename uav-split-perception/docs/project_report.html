Project report · uav-split-perception

AEGIS-UAV: split computing vs. image offloading for drone object detection

A complete account of everything done in this folder — what the project is, what state it was in, every problem found, how each was fixed and why, how the experiments work, what they show, and how the final paper and its evidence fit together.

Start hereSummary in one page

The question. A drone (UAV) films at 30 frames per second and needs objects detected (people, cars, …). Its onboard computer is slow and battery-limited; a ground server with a GPU is fast but reachable only over an unreliable wireless link. There are three ways to run the detector:

  1. Onboard only — run the whole neural network on the drone. No network needed, but slow.
  2. Image offloading — compress each frame as a JPEG and send it; the server runs the network.
  3. Split computing — run the first few layers on the drone, send the intermediate “feature maps” (compressed), and the server runs the rest.

Split computing is often promoted as the best of both worlds. The project asks honestly: when does it actually pay off?

What happened in the folder. The original code (written 22–23 Sep 2026 in 18 commits) claimed strong results, but the first audit found that many were not real: a fake H.264 codec, invented hardware measurements, copied accuracy rows, a simulator that broke physics, and bugs that quantized the wrong tensors. The owner pushed 7 fix commits (25–26 Sep); a second audit found some fixed, some not, and a few new problems. Then the whole project was rebuilt on a branch called publication-overhaul: every module rewritten or verified, an automated test suite, every experiment re-run on the full 5,000-image COCO validation set, a new simulator and adaptive policy, and a new paper in which every number is generated from the result files. A third audit (28–29 Sep, Part XIII) then checked the paper against the data, the code and its own mathematics. It fixed nine code bugs and a simulator energy error, added a SymPy proof checker for every equation, corrected two propositions and two overstated conclusions, and verified and completed the bibliography. Today 106 tests pass, and 200 numbers in the paper text are generated macros.

What the evidence says.

  • The split engine is bit-exact: splitting YOLOv8s at any of its 22 layer boundaries gives exactly the same output as the unsplit model.
  • INT8 compression of the split tensors costs at most 0.04 mAP points (baseline 44.4) — statistically indistinguishable from no loss.
  • But even the smallest split payload (layer 4, INT8 + zstd: 310.7 KiB) is 2.4× larger than a JPEG at quality 95 (130.9 KiB, −0.21 mAP) and 3.4× larger than JPEG quality 90.
  • So in the trace-driven simulation, JPEG offloading beats every fixed split configuration in all 16 network/hardware scenarios. Split computing beats running onboard in 10 of 16 (fast links or slow drones).
  • An uncertainty-aware adaptive policy that picks per moment among onboard / split / JPEG matches or beats fixed JPEG in all 16 settings (1.00–1.26×), mostly by switching to a smaller JPEG when the link weakens. Over 1,300 randomly drawn systems it falls below fixed JPEG Q90 in 112, by at most 7 %.
  • With many drones sharing a cell, split's bandwidth need makes it collapse first (6.5 → 0 fps at 20 UAVs); relaying through a neighbour drone did not help.

Generalized (Part XII). The same answer holds across 19 detectors, 5 input sizes, aerial imagery, every bit width and 1,300 randomly drawn systems; a closed-form model shows why: whenever the image needs fewer bits and less onboard work, a split can win by at most its accuracy ratio (≤ 0.5 %).

The one-sentence takeaway: for a single-frame detector like YOLOv8 on a UAV, split computing is exact, nearly free in accuracy and often better than onboard inference on a slow drone, but its intermediate tensors are too big to beat a well-tuned JPEG (it lost in all 16 system settings and won in only 33 of 977 feasible random systems, by at most 0.47 %); the next thing to try is a learned bottleneck, not post-hoc quantization.

Part IBackground from the basics

This part explains every idea the project uses, starting from zero, so the later parts can be followed without prior knowledge.

1. Object detection and YOLOv8

Object detection means: given an image, output a list of boxes, each with a class label (“person”, “car”, …) and a confidence score. It is harder than classification (one label per image) because the model must also say where each object is.

A convolutional neural network (CNN) is a stack of layers. Each layer takes a 3-D array (a tensor of shape channels × height × width) and produces another. Early layers detect edges and textures at high resolution; later layers detect object parts and whole objects at lower resolution but with many channels. The output of a layer is called a feature map or activation.

YOLO (“You Only Look Once”) detectors predict all boxes in a single forward pass, which makes them fast. The project uses YOLOv8s (the “small” variant from Ultralytics):

  • 11.17 million parameters (weights), 14.4 G multiply-accumulate operations (MACs) per 640×640 image = 28.8 GFLOPs (one MAC = 2 floating-point operations; the original code confused the two).
  • 23 modules numbered 0–22: a backbone (0–9: Conv, C2f blocks and SPPF) that extracts features; a neck (10–21: upsampling, concatenation, C2f) that merges scales; and a Detect head (22) that outputs boxes at three scales (strides 8, 16, 32).
  • Skip connections: the neck re-uses outputs of earlier layers — e.g. layer 12 concatenates with layer 6's output, layer 15 with layer 4's. This matters enormously for splitting (next sections).

After the network, non-maximum suppression (NMS) removes duplicate overlapping boxes, keeping the most confident.

2. Measuring accuracy: IoU, precision/recall, mAP

IoU (Intersection over Union) of a predicted box and a true box = area of overlap ÷ area of union. A prediction counts as correct (“true positive”) if its IoU with an unmatched true box of the same class is above a threshold.

Precision = fraction of predictions that are correct; recall = fraction of true objects found. Sorting predictions by confidence and sweeping a threshold gives a precision–recall curve; its area is the Average Precision (AP) of one class.

mAP = AP averaged over the 80 COCO classes. mAP@0.5 uses an IoU threshold of 0.5; mAP@[.5:.95] (the main COCO metric, used throughout) averages over IoU thresholds 0.50, 0.55, …, 0.95, rewarding precise localization. It is reported ×100, “in points”. YOLOv8s on COCO val2017 scores 44.4 (and 61.1 at IoU 0.5) in this project's measurement.

COCO val2017 is the standard 5,000-image validation set (4,952 have labels). The original project evaluated on COCO128, 128 images that are actually training images — too few, and ones the model has seen, so the numbers were optimistic and noisy.

3. Split computing

Run layers 0…k on the drone (the edge), send what is needed, run layers k+1…22 on the server (the cloud). The cut position k is the split point.

The live set. Because of skip connections, the cloud may need more than layer k's output. For example, if we cut after layer 9, the cloud still needs layers 4 and 6 (used by the neck later). The set of tensors that must cross the cut is called the live set. For YOLOv8s:

The original code sent only layer k's output for k≥5, which is why its accuracy numbers were wrong (it silently used unquantized skip tensors).

4. Quantization

Activations are 32-bit floats (FP32, 4 bytes each). Quantization stores them with fewer bits. The schemes used:

  • Per-tensor symmetric INT8 (the main one). One scale S for the whole tensor:
    S = max|X| / 127 (rounded to float32) q = clamp(round(X / S), −128, 127) → 1 byte per value X̂ = q · S (reconstruction on the server)
    Rounding to the nearest integer means each value is off by at most half a step: ‖X − X̂‖∞ ≤ S/2. This bound is proven in exact arithmetic; in float32 there is an extra tiny slack ≤ 2ε·max|X| (ε ≈ 6×10⁻⁸), which the tests account for.
  • Per-channel INT8 — one scale per channel; more precise when channels have very different ranges.
  • Affine UINT8 — maps [min, max] onto 0…255 with a zero-point; suits non-negative data.
  • UINT8 with 99.9 % clipping — ignores the top 0.1 % of values to get a finer step; saturates outliers.
  • FP16 — half-precision floats, 2 bytes.
  • INT8 → FP16 accumulate — dequantize directly into half precision.

SQNR (signal-to-quantization-noise ratio, in dB) = 10·log₁₀(signal power ÷ error power); higher is better. Measured: INT8 28.3 dB, per-channel 35.2 dB, FP16 73.6 dB.

5. Compression and codecs

  • Lossless compression (zstd) — Zstandard, a fast general-purpose compressor. Applied to the INT8 bytes it shrinks split payloads 2.3–2.6× with zero information loss (activations after SiLU have many repeated small values).
  • JPEG — lossy image codec (DCT + quantization + entropy coding) tuned to human vision. Quality Q from 1–100. Encoding a 640×640 frame takes ≈ 1 ms.
  • WebP — Google's image codec, often smaller than JPEG at equal quality.
  • H.264 — video codec. Used here in intra-only mode (every frame self-contained, as a lost packet must not corrupt later frames) via ffmpeg/libx264, “ultrafast/zerolatency”, quality controlled by CRF (lower = better). The original repository claimed H.264 but actually called WebP.

The central comparison of the paper is bytes sent vs. accuracy kept — the rate–accuracy trade-off.

6. Wireless channels

A drone's uplink quality varies over time. The standard way to describe it:

  • SINR (signal-to-interference-plus-noise ratio, dB) — how much stronger the wanted signal is than the noise.
  • Shadowing — slow variation caused by buildings/terrain, modelled as log-normal (normal in dB). Gudmundson's model makes it correlated over distance: an AR(1) process where each value is mostly the previous one plus a small random change.
  • Fast fading — rapid fluctuation from multipath. Rician fading applies when there is a line-of-sight path (common for drones). Its speed depends on Doppler (speed × carrier frequency 3.5 GHz); generated with the Clarke/Jakes sum-of-sinusoids method.
  • Shannon capacity C = B·log₂(1 + SINR) is the theoretical maximum. Real LTE/5G gets less; 3GPP TR 36.942 gives a standard “attenuated and truncated” mapping: throughput = α·B·log₂(1+SINR), capped at a maximum spectral efficiency and zero below a minimum SINR (here α = 0.4, max 2 bit/s/Hz uplink, SINR_min = −10 dB).
  • Blackout — total loss of the link (e.g. flying behind a building).
  • Cell capacity sharing — many drones in one cell split its capacity; water-filling gives each user what it asks for until capacity runs out, then shares the rest equally.
  • A2A relaying — drone-to-drone links (Wi-Fi 802.11ax) let a drone with a bad uplink forward data through a neighbour.

7. UAV power and energy

A quadcopter spends most of its energy just staying in the air. Momentum theory gives the ideal hover power from thrust T and induced velocity vi; dividing by the rotor figure of merit and motor efficiency gives the real value:

P_hover = T · v_i / (FoM · η) ≈ 109.9 W (for this project's airframe)

Compared to that, compute (≈10 W) and radio (≈3.8 W transmitting) are small. This is why the original “74 % energy savings” claim was misleading: it compared compute energy alone. With hover included, flight endurance varies only between 24.2 and 25.1 minutes across strategies (55.5 Wh battery, 15 W avionics).

8. Statistics used

  • Paired bootstrap confidence interval. To know if configuration B is really worse than A (and not noise), resample the 5,000 images with replacement many times, recompute mAP(B) − mAP(A) on each resample using the same images for both (paired), and take the 2.5th and 97.5th percentiles as a 95 % CI. If the CI contains 0, the difference is not significant. The project uses 300 resamples for accuracy and 200 for codecs.
  • Student-t confidence intervals for simulator results over 5 random seeds (t0.975,4 = 2.776 × standard error).
  • EWMA (exponentially weighted moving average) — running estimate that weights recent samples more; used by the adaptive policy to predict bandwidth.
  • Normal tail probability — P(goodput ≥ needed) assuming goodput ~ Normal(mean, std); used to estimate the chance of meeting a deadline.

1. The split engine — core/

What core/dynamic_submodels.py was rewritten. It builds an edge submodel (layers 0..k) and a cloud submodel (k+1..22) for any k, and core/submodels.py keeps the old named classes as thin subclasses.

How

  • analyze_split_dependencies(seq, k) walks each layer's f (“from”) field to find which earlier outputs later layers read; the live set = outputs produced at or before k that are read after k.
  • The edge submodel returns a dict of all live tensors; the cloud submodel checks it received exactly the tensors it needs (required_inputs) and rejects anything else.
  • verify_arbitrary_split_parity runs every cut 0..21 and checks the split output equals the full model's with tolerance 0 (bit-exact). It passes on all 22.
  • save_submodel_checkpoint writes a self-describing file (format tag, role, cut, architecture, activation types, weights), loadable without the original model.
  • DynamicCloudDispatcher serves every cut from one shared copy of the weights (11.17 M params instead of 80.8 M), and strictly validates split codes (rejects “k-3”, “kx”, 100).
  • core/inspect_graph.py reports MACs vs FLOPs correctly, the live set and payload for every cut, and writes configs/split_config.yaml and the topology JSON used by the paper.

Why The whole study rests on the split being correct. Bit-exact parity proves any accuracy change is due only to compression, never to a splitting bug. The live-set analysis fixed the original's biggest bug (skip tensors ignored).

2. Quantizer — quantization/quantizer.py

What Fixed and hardened all quantization modes.

How The scale is computed and stored as float32 (no truncation later); division is done by a float32 tensor, not a Python number; per-channel scales keep their 3-D shape; the 99.9 % percentile uses kthvalue (exact, no memory blow-up); int8_fp16_accum computes in FP16 and returns the requested dtype; an unknown mode raises an error instead of silently doing nothing.

Why Dividing by a Python scalar on a CUDA GPU makes PyTorch multiply by the reciprocal instead — a result can differ by one step from the CPU. Dividing by a tensor gives identical results on CPU and GPU, which is required for the CUDA kernel to match bit-for-bit and for the error bound to hold everywhere.

3. Wire protocol — protocol/

What protocol/packet.py rewritten into a strict, “fail-closed” binary format; transport.py fixed.

How Layout of one packet:

[16-byte header <BIQBBB : version, frame id, timestamp, split, dtype, n_tensors, flags] [16-byte descriptor per tensor <BBHHHfI : layer, dtype, C, H, W, scale, payload length] [payloads … (per-channel scales / zero-point prefix if needed; optional zstd)] [optional 32-byte HMAC-SHA256 if FLAG_HMAC=0x80] [4-byte CRC32]

The parser rejects: bad CRC, wrong version, bad or missing HMAC, unknown dtype, zero-size or oversized dims (>65535), duplicate layers, trailing bytes, decompression bombs (limit on output size), inconsistent flags, and mixed dtypes. It raises a single CorruptedPacketException which the server catches and logs (throttled) instead of crashing. Transport uses one ZeroMQ context, send timeout 5 s, linger 1 s and a 64 MiB max message size.

Why A drone link is noisy and possibly hostile. “Fail-closed” means anything not exactly right is dropped, never half-used. CRC detects corruption; HMAC (with a shared key) proves the packet came from our drone and wasn't modified.

4. Pipelines and demo — pipeline/, demo/, simulation/channel_proxy.py

  • Edge pipeline: reads real frames (COCO images or video) with the same letterbox resize as Ultralytics, stamps the capture time, supports auth keys, and refuses the “full” mode (nothing to send).
  • Cloud pipeline: robust handle() that survives bad packets, uses Ultralytics' own NMS, bounded history, idle timeout.
  • Runtime switchboard (dynamic_policy.py): uses the same AdaptivePolicy as the simulator, producing JPEG, split packet, or onboard output per frame.
  • Demo: letterbox + proper NMS, blackout drops offloaded frames, synchronized GPU timing, and a label saying transmission is simulated.
  • Channel proxy / netem: reports “not valid” until data arrives, tracks staleness, never dies silently; netem only replays traces with tc.

Why The live system must behave like the paper describes, and must not pretend (the old demo implied real transmission).

5. CUDA kernel and export — deployment/jetson/

What The C++/CUDA INT8 quantizer was fixed and, for the first time, compiled and tested.

How Uses rintf (round-half-to-even like PyTorch) and __fdiv_rn (IEEE-correct division), runs on the current CUDA stream, no memory allocation per call, full error checks, 64-bit indexing. Test: 50 random tensors, output bit-identical to Python on CPU and GPU. export_trt.py exports TorchScript and verifies it (max difference 0.0); ONNX/TensorRT steps report “skipped” honestly because those packages aren't installed.

Why Claiming a Jetson kernel that was never run was one of the original false claims; now what is claimed is exactly what is tested.

The hooks trick (important). Instead of physically splitting the model for accuracy runs, install_split_quant_hooks attaches small functions to the unsplit model: a forward hook on layer k replaces its output with quantize→dequantize(output); for skip tensors (e.g. layer 4 when k = 9) a pre-hook on the cloud layer that reads it quantizes it only there — so edge layers still see full precision, exactly like a real split. This lets the standard Ultralytics validator compute official mAP.

Per-image statistics. capture_per_image_stats temporarily intercepts Ultralytics' metric processing to save per-image true-positive/confidence/class arrays; the bootstrap then recomputes mAP on resampled images without rerunning the network.

Part VIMethodology — how each experiment works

1. Accuracy experiments

  1. Load YOLOv8s pretrained weights; run Ultralytics validation on all 5,000 COCO val2017 images, batch size 1 (so each image gets its own quantization scale, as on a real drone), 640 px.
  2. For each configuration (cut k, mode), install the hooks, validate, save per-image stats (cached in experiments/cache/val_stats so re-runs are instant).
  3. Compare with baseline via paired bootstrap (300 resamples; resample r uses seed 100003·seed + r so results don't depend on how many CPU workers run it). Workers use the “spawn” method to be safe with PyTorch threads.

2. Codec experiments

Each image is letterboxed to 640×640, encoded (JPEG/WebP via OpenCV — with an RGB→BGR fix, since OpenCV expects BGR; H.264 via ffmpeg libx264 intra-only), decoded, and fed to the model via a pre-forward hook. Sizes are averaged; accuracy compared with 200 bootstrap resamples. Rates are cached.

3. Timing and payload

On the host GPU (RTX 4050 Laptop), 200 frames per configuration, with CUDA synchronization so each stage (edge DNN, quantize+serialize, deserialize+dequantize, cloud DNN, NMS) is timed separately. Full model 11.93 ms; k4 INT8 end-to-end 13.33 ms.

4. The system model (what's modelled, not measured)

  • One hardware knob, tfull = time for the drone to run the full model: 40, 90, 180, 360 ms (fast Jetson-class to slow microcontroller-class). Onboard edge time for cut k = tfull × FLOP fraction of k. Other onboard work (quantization, JPEG encoding) is scaled by the same slowdown factor tfull/11.93 ms — so no strategy gets an unfair speed advantage.
  • Power: compute 10 W busy / 2 W idle, modem 3.8 W transmit / 1.2 W idle, A2A radio 1.5 W, hover 109.9 W (momentum theory, 1.2 kg, 0.2 m² rotor area), avionics 15 W, battery 55.5 Wh.
  • Deadline: a frame's result counts only if ready within 300 ms of capture (“on-time”). Main metric: on-time FPS (of 30 possible).

6. The simulator

  • Time moves in 10 ms slots; camera produces a frame every 33.3 ms.
  • The onboard processor does one job at a time; if busy, new frames are skipped. The uplink buffer keeps only the newest frame (old ones are useless for real-time).
  • Delivered data per slot = bandwidth × (1 − loss). A transfer still going after the 300 ms deadline is aborted (don't waste the channel).
  • A frame is on time if its result is ready within 300 ms of capture: at the server for offloaded frames, onboard (after tfull) for onboard inference.
  • Energy is the busy-time-weighted increment above idle. A drone's modem is charged once for the time any of its frames is on air, own or relayed (corrected in audit 3).
  • Swarm: N drones in one 100 Mbps cell; capacity shared by water-filling. Relaying: a drone may forward via a neighbour over 802.11ax (log-distance path loss → MCS table → rate × 0.65 MAC efficiency).
  • Every result: 5 seeds, mean ± 95 % t-interval. Results are cached per cell with a SHA-256 fingerprint of the inputs and the simulator source code, so any code change invalidates stale results automatically.

7. The adaptive policy

Every decision, for each candidate c (onboard, each split, JPEG), the policy computes:

score_c = f_c · p_c · A_c / A_ref − λ_E · E_c λ_E = 0.05 per (s·J) p_c = P(B ≥ B*_c) = ½·erfc((B*_c − μ) / (√2·σ)), B*_c = b_c / (D − e_c − d − s_c) p_c = 0 if D ≤ e_c + d + s_c (no time left) or μ ≤ 0.001 Mbit/s; onboard: p_c = 1 if t_full ≤ D f_c = F / ceil(F · max(e_c, b_c/μ)) frames/s on camera ticks E_c = (P_busy − P_idle)·e_c + (P_tx − P_rx)·b_c/μ joules per frame μ, σ = EWMA of goodput (τ = 200 ms), σ ≥ 0.1·μ; d = 20 ms assumed one-way delay A_c / A_ref = mAP of configuration c over the unsplit FP32 mAP

It picks the highest score, but only switches if the new option is ≥ 5 % better (hysteresis, to avoid flapping). Two variants: adaptive_split (onboard or splits only) and adaptive_all (also JPEG).

Why this design The first version maximised a power-weighted score and learned that doing nothing is cheapest — it got 0.32× the best fixed strategy. Rewarding expected on-time, accuracy-weighted throughput with uncertainty fixed that.

Part XLimitations and open items

Limitations (stated in the paper)

  • Onboard speed and power are parameters, not measurements; the sweep bounds their effect. Onboard non-DNN work (including JPEG encoding) is scaled like the DNN, which is conservative for JPEG because embedded SoCs usually encode JPEG in hardware.
  • Channel traces are synthetic; measured traces in the same CSV format can be dropped in.
  • Aerial imagery is evaluated only zero-shot (COCO-trained detectors on VisDrone mapped to COCO classes), and the Monte Carlo uses YOLOv8s payloads and timings.
  • Single-frame H.264 understates video coding efficiency, which would only widen the gap in favour of image offload.
  • Swarm policies act independently; the air-to-air model omits interference between concurrent links and relative motion.
  • For offloaded frames, latency is measured to result availability at the server; returning results adds one more one-way delay.
  • No learned feature compression (bottleneck autoencoders), which could shrink split payloads below JPEG — the main direction in which split computing could win.

Likely questions

Q: Your result is negative for split computing — why publish it?

Because it tells practitioners when not to use it and quantifies the break-even. Negative results backed by exact, reproducible measurement are valuable; they also point to what is needed (learned compression below ~90 KiB).

Q: How do you know the accuracy change comes from quantization, not a bug?

Without quantization, every one of the 22 cuts is bit-identical to the full model (tolerance 0, automated test). Any change is therefore from compression alone.

Q: Why batch size 1 in validation?

A drone processes frames one at a time, so each frame gets its own quantization scale. Larger batches would share a scale across images and misrepresent the real system.

Q: Why paired bootstrap rather than just comparing mAP?

Differences of 0.01–0.3 points are within noise unless tested. Pairing (same images in both configurations) removes the variation due to image difficulty and gives tight intervals.

Q: Your hardware isn't a real drone computer.

Correct, and the paper says so. Instead of one guessed device, onboard speed is swept from 40 to 360 ms, and all onboard work is scaled consistently. The conclusions hold across the sweep.

Q: Why not split at k9 or later, where the drone does more work?

Skip connections force several tensors across the cut — 1.4 MB INT8 — larger than the raw image. k4 is the only bottleneck in YOLOv8s.

Q: Why is energy not a differentiator?

Hover takes ≈110 W; compute and radio are ≈4–14 W. Endurance changes by under a minute (24.2–25.1 min) across strategies.

Q: Why synthetic traces?

No measured UAV traces were available; the generator uses standard models (Gudmundson shadowing, Rician fading, 3GPP TR 36.942 mapping) and the CSV format accepts measured traces directly.

Q: What does HMAC add over CRC?

CRC catches accidental corruption but anyone can recompute it. HMAC-SHA256 needs a secret key, so a forged or tampered packet is rejected.

Q: How can someone check your numbers?

Run make reproduce. Every number in the paper is a macro generated from result files, and docs/claims_to_evidence.md lists each one with its source.

Q: How do you know the equations are right?

scripts/verify_math_proofs.py proves each derivation with SymPy where it can, checks the rounding steps (ceil, max) on tens of thousands of exact-rational cases, and confirms that the code evaluates each printed formula. It also compares every stated constant with the code and data. All 40 checks pass, and the script fails if any of them breaks later.

Q: Does a split ever beat JPEG?

Not in the 16 main settings. In 977 feasible random single-UAV systems it wins 33, by at most 0.47 %, and never by more than the accuracy-ratio bound of Proposition 2. The paper states this rather than “never”.

2. The general model (works for any numbers)

How Every strategy c is described by just a few numbers: φc (share of the network's work done on the drone), ρc (other onboard work such as quantizing or JPEG encoding, relative to the full model), bc (bits sent), sc (server time) and Ac (accuracy; Aref is the unsplit FP32 model's). With onboard full-model time tfull, goodput B, delay d, deadline D and camera rate F:

onboard time e_c = t_full·(φ_c + ρ_c) latency L_c = e_c + b_c/B + d + s_c bandwidth needed for the deadline B*_c = b_c / (D − e_c − d − s_c) (∞ if D ≤ e_c + d + s_c) frame rate f_c = F / ceil(F · max(e_c, b_c/B)) utility U_c = f_c · [B ≥ B*_c] · A_c / A_ref (accuracy-weighted on-time detections per second) onboard nothing is sent: latency t_full, on time if and only if t_full ≤ D

From these, four general statements follow. They are Propositions 2–5 in Section VII of the paper; Proposition 1 is the INT8 error bound. Code: simulation/analytic.py; each is checked by scripts/verify_math_proofs.py.

  1. Offload dominance. If the image needs no more bits and no more onboard work than the split, then for every bandwidth, delay, deadline, frame rate and swarm size, the image is at least as fast, needs less bandwidth, uses less energy, and the split can win by at most its accuracy ratio Asplit/Aimage (for the k4 split: 0.4 % vs JPEG Q95, 0.7 % vs Q90). For YOLOv8s this condition holds on any drone computer slower than about 13 ms per inference — i.e. every realistic embedded board.
  2. Split vs onboard break-even. Offloading beats running onboard only when β = B·tfull / b > 1 — the link must send one payload faster than the drone can run the whole model — the onboard work is less than the full model, and the deadline is met. This break-even is necessary but not sufficient: because frames arrive on camera ticks, the exact threshold is max(B*, F·b / (⌈F·tfull⌉ − 1)).
  3. Swarm capacity. Water-filling gives each drone at least min(own goodput, C/N). If every drone's own goodput is at least B*, a cell of capacity C keeps N ≤ C / B* drones on time, so two options support swarm sizes in inverse proportion to their payloads.
  4. Energy bound. Perception can change endurance by at most [(Pbusy−Pidle) + (Ptx−Prx)] / (Phover + Pav + Pidle + Prx), which is small unless the drone is tiny.

Why The first statement removes the channel, deadline, frame rate and swarm size from the split-vs-image question entirely: it reduces to bytes and accuracy, which can be measured once per model. That is why the next measurements focus on payload ratios.

3. Other detectors, sizes and aerial images

  • Exactness everywhere: all 19 detectors split bit-exactly at every one of their 432 cut points.
  • Payload: the smallest split payload (INT8 + zstd) is 2.0× (YOLO11n) to 11.5× (YOLO11x) a JPEG Q90 frame and at least 1.4× a JPEG Q95. No model comes below JPEG. For 18 of 19 the best cut is the end of the stride-8 stage (k3/k4); YOLOv9m's is at layer 1.
  • Bigger models are worse for splitting — their early feature maps have more channels, while the image stays the same.
  • A stronger compressor doesn't help: zstd level 19 instead of level 1 saves at most 3.4 %.
  • Accuracy (10 detectors, all 5,000 COCO images): INT8 split costs at most 0.05 points (significant for only 1 model); 6 bits costs 0.12–0.35; 4 bits costs 5.8–20.4. JPEG Q90 costs 0.19–0.80 but needs 2–8× fewer bytes than the INT8 split.
  • Resolution (YOLOv8s): the ratio grows from 3.4× at 320 px to 5.3× at 1280 px, because JPEG exploits the extra redundancy of bigger images. Across all 43 model/size/imagery combinations the smallest ratio is 2.0×.
  • Aerial (VisDrone, 548 images, COCO-trained models applied zero-shot with labels mapped to COCO classes): ratio 3.2× at 640 px and 4.0× at 1280 px. At 1280 px, YOLOv8s INT8 split (901 KiB) costs −0.02 and JPEG Q95 (299 KiB) −0.04 — neither significant. Small aerial objects do not make high-quality JPEG disproportionately harmful.

6. The generalized conclusion

For any unmodified CNN detector of the YOLO kind, at any input size, on ground or aerial imagery, with any network, hardware, deadline, frame rate or swarm size we could sample: splitting is exact and INT8 is lossless in practice, but the smallest split payload is 2–11.5× a JPEG frame, so whenever the image also needs less onboard work (any drone computer slower than ~13 ms/inference) a split can beat image offload by at most its tiny accuracy ratio. Whether to offload at all versus run onboard is decided mainly by onboard speed and goodput (β = B·tfull/b > 1). An adaptive policy that can use onboard, split and JPEG is near-optimal almost everywhere: at least 90 % of the hindsight-best fixed option in 99.8 % of single-UAV scenarios.

What Every network element of the simulator was rebuilt in ns-3.48 and OMNeT++ 6.3 (INET 4.5.4, Simu5G 1.6.0), and the frame pipeline was run over the real Linux stack (30 Sep 2026).

Why A simulator written by the authors is only credible if independent tools reproduce its answers; before this, the OMNeT++ files in the archive had never run.

We therefore rebuilt every network element of the study in two independent packet-level simulators, ns-3.48 and OMNeT++ 6.3 (with the INET 4.5.4 and Simu5G 1.6.0 libraries), and ran the real Linux network stack with the real frames, codecs and models. Problems met during validation

  • ns-3 goodput window included a 0.5 s tail (fixed); default −82 dBm preamble detection capped range at ~294 m (now both receivers are run).
  • INET: the band parameter was set on the wrong module (radio ran at 2.4 GHz), and **.mobility.typename gave each antenna a randomly placed mobility module, so the two UAVs were ~1 km apart; both fixed.
  • Simu5G: PF starvation at N ≥ 10 is a property of its scheduler (MAX-C/I serves all); large bursts are lost (RLC UM) or delayed (RLC AM), so O3 is not usable; saturated runs at N ≥ 10 needed >3 GB, so runs are memory-capped.
  • Emulation: the ACK/result wait halves throughput; the simulator reproduces it with the same release rule.
  • Packet-forwarding relay option: a first version stalled frames through a floating-point cap and hid in-flight frames from relay selection; both fixed, with regression tests, before any number was used.
